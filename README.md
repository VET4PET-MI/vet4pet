## 1. תקציר הפרויקט

**מטרת הפרויקט.** VET4PET היא פלטפורמה דיגיטלית לניהול הפן הבריאותי של חיית המחמד. המערכת מרכזת במקום אחד את המידע הרפואי של החיה — סיכומי ביקור, חיסונים, בדיקות, צילומים ומרשמים — מאפשרת ניהול תורים מול המרפאה הווטרינרית, ומספקת ערוץ תקשורת מרחוק בין הבעלים לווטרינר בהודעות טקסט ובשיחת וידאו. בנוסף ניתן לאתר וטרינר זמין לפי מיקום במקרה חירום.

**קהל היעד.** שני סוגי משתמשים, המוגדרים במערכת כתפקידים נפרדים:

- **בעלי חיות מחמד** — צפייה בתיק הרפואי, ניהול פרטי החיה, קביעת תורים, פנייה לייעוץ מקוון ואיתור וטרינר חירום.
- **וטרינרים ומרפאות** — הזנת רשומות רפואיות והעלאת מסמכים, ניהול יומן ושעות פעילות, מענה לפניות ייעוץ ותקשורת עם הלקוחות.

**מה כולל הפרויקט.** המאגר בנוי כ-monorepo ומכיל שלושה רכיבים הניתנים לפריסה עצמאית, הפונים כולם לאותו REST API:

| תיקייה | תוכן |
|---|---|
| `android-app/` | אפליקציית Android נייטיב בשפת Kotlin |
| `web-app/` | אתר אינטרנט מבוסס React |
| `backend/` | שרת Node.js/Express החושף REST API מול MongoDB |
| `docs/submitted/` | מסמכי ההגשה: נושא הפרויקט, מסמך דרישות, Detailed Design, מסמך שינויים, PROTOTYPE, סקירה ספרותית ומצגת |
| `docs/superpowers/` | מסמכי אפיון פנימיים לשתי תוספות מאוחרות |

**חשיבות הפרויקט.** כיום המידע הרפואי של חיית המחמד מפוזר בין מרפאות שונות ונגיש בפועל רק לווטרינר המטפל, כך שהבעלים תלוי בפנייה יזומה למרפאה כדי לדעת מה נעשה ומתי. הפרויקט נועד לרכז מידע זה במקום אחד ולאפשר תקשורת יעילה בין בעלי החיות לבין הווטרינר. שילוב האפליקציה, האתר והשרת מספק פתרון אחד לניהול התהליך הרפואי מתחילתו ועד סופו — מתיעוד הביקור, דרך זימון התור הבא, ועד ייעוץ מרחוק במקרה הצורך.

## 2. מרכיבי המערכת

**אפליקציית Android.** אפליקציה נייטיב בשפת Kotlin, בנויה בתבנית MVVM עם מסך יחיד המארח מסכי משנה וניווט מרכזי. התקשורת עם השרת נעשית ב-Retrofit, וטוקן ההזדהות מצורף אוטומטית לכל בקשה. האפליקציה תומכת בשני התפקידים: הבעלים מנהל את חיותיו וקובע תורים, והווטרינר מחפש מטופל, מזין רשומות רפואיות ומנהל יומן. קיים מטמון מקומי המאפשר תצוגת מידע גם ללא רשת, וכן תמיכה מלאה בעברית ובאנגלית כולל פריסת RTL.

**אתר Web.** אפליקציית React הנבנית ב-Vite ומעוצבת ב-Tailwind CSS. ההרשאות נאכפות בשכבת הניווט: מסלול מוגן דורש משתמש מחובר, ומסלולים ייעודיים מוגבלים לתפקיד יחיד — למשל יומן המרפאה ורשימת המטופלים לווטרינרים בלבד, וקביעת תור ואיתור חירום לבעלים בלבד. האתר דו-לשוני (עברית/אנגלית).

**Backend.** שרת Node.js עם Express, במבנה שכבות מפורש המפריד בין הגדרת הנתיבים, הלוגיקה העסקית ומודל הנתונים. כל נתיבי ה-API מלבד ההרשמה וההתחברות מחייבים טוקן תקף, ונתיבים רגישים מוגבלים בנוסף לפי תפקיד. קיים טיפול שגיאות מרכזי המחזיר תשובות בפורמט JSON.

**מסד הנתונים.** MongoDB (NoSQL) מול Mongoose כשכבת מידול וּולידציה. המערכת מנהלת תשעה אוספים: משתמשים, חיות מחמד, רשומות רפואיות, תורים, פניות ייעוץ, הודעות, התראות, חסימות זמן ולוח שעות עבודה.

**שירותים חיצוניים.**
- **Cloudinary** — אחסון תמונות ומסמכי PDF מחוץ לשרת, עם סינון סוגי קבצים ומגבלת גודל.
- **Firebase Cloud Messaging** — התראות Push למכשירי Android, הנשלחות מהשרת.
- **Jitsi Meet** — תשתית שיחות הווידאו. השרת מייצר חדר ייחודי לכל פנייה, ושני הצדדים מצטרפים לאותה כתובת: באפליקציה בתצוגה מוטמעת, ובאתר בלשונית דפדפן.
- **Render / Vercel** — סביבות ההרצה בענן: השרת פרוס ב-Render והאתר ב-Vercel.

## 4. מה תוכנן לעומת מה מומש

**כל היכולות הפונקציונליות המרכזיות שהוגדרו במסמכי הדרישות מומשו במלואן**, לרבות יכולות שסומנו במקור כאופציונליות. הפערים המפורטים בהמשך נוגעים להיבטים טכניים ולשיפורים עתידיים, ולא לחוסר במימוש של יכולת מרכזית כלשהי.

### יכולות שתוכננו ומומשו

| דרישה מהאפיון | מצב המימוש |
|---|---|
| ניהול משתמשים: הרשמה, התחברות מאובטחת, פרופיל בעלים ופרופיל חיה, תמיכה במספר חיות לבעלים | מומש |
| תיק רפואי דיגיטלי: היסטוריית טיפולים וחיסונים, הזנת סיכומי ביקור ע"י הווטרינר, העלאת מסמכים ותמונות | מומש, עם שמונה סוגי רשומה; הרשאת הכתיבה שמורה לווטרינר בלבד |
| ניהול תורים: קביעה, ביטול, שינוי מועד וניהול יומן זמינות | מומש, כולל חישוב אוטומטי של חריצי זמן פנויים |
| רפואה אונליין: פתיחת פנייה, צ'אט בין הבעלים לווטרינר ותיעוד אוטומטי של הייעוץ בתיק | מומש; בסיום ייעוץ נוצרת אוטומטית רשומה רפואית הכוללת את משך השיחה |
| ייעוץ וידאו (הוגדר במסמך הדרישות כאופציונלי / Advanced MVP) | מומש, כולל הטמעה בתוך האפליקציה |
| חירום: איתור וטרינר זמין לפי מיקום | מומש, עם סינון וטרינרים תורנים ומיון לפי מרחק |
| התראות: תזכורות לתורים ולחיסונים | מומש, באמצעות משימה יומית מתוזמנת בשרת והתראות Push |
| אבטחה: הרשאות מבוססות תפקיד, הצפנת תקשורת וגיבוב סיסמאות | מומש |
| טעינה מדורגת של התיק הרפואי | מומש כעימוד בצד השרת |
| ממשק רספונסיבי | מומש באתר, כולל תמיכת RTL |
| בחירות הטכנולוגיה (Kotlin, React, Node/Express, MongoDB, JWT, Cloudinary) | מומש במלואו, ללא סטייה מהמתוכנן |

### פערים

1. **היקף הבדיקות האוטומטיות.** ה-Detailed Design ייעד מסגרות בדיקה אוטומטיות רחבות יותר מאלה שהוטמעו בפועל. תהליך האימות של המערכת נשען בעיקרו על בדיקות ידניות מקיפות (ראו פרק 6), בעוד הכיסוי האוטומטי מצומצם. זהו תחום ההרחבה הטבעי הראשון של הפרויקט.
2. **מניעת התנגשות בהזמנת תור בו-זמנית.** המערכת מציגה למשתמש אך ורק חריצי זמן פנויים ומסננת תורים קיימים וחסימות יומן. עם זאת, במצב מירוץ נדיר שבו שני משתמשים מזמינים את אותו חריץ באותו רגע ממש, אין חסימה נוספת ברמת השרת. שיפור המנגנון הוגדר כבר במסמך ה-PROTOTYPE כמשימת המשך.

מעבר לאמור לעיל, לא נמצאה יכולת פונקציונלית שהוגדרה במסמכי האפיון ולא מומשה.

## 5. תוספות מעבר לתכנון

במהלך הפיתוח נוספו גם היכולות הבאות, מעבר למסמך הדרישות המקורי:

1. **ניהול זמינות גרנולרי ליומן הווטרינר** — הגדרת ימי ושעות עבודה קבועים, לצד חסימת חלונות זמן נקודתיים (הפסקה, ניתוח חירום), ששניהם נלקחים בחשבון בחישוב החריצים הפנויים.
2. **חיפוש מבוסס תעודת זהות מטעמי חיסיון רפואי** — הווטרינר אינו מקבל רשימה של כלל בעלי החיים, אלא נדרש לחפש באופן אקטיבי לפי ת"ז של הבעלים. נוספה ולידציה מלאה של תעודת זהות ישראלית בשרת ובאפליקציה.
3. **הודעת מערכת אוטומטית בעת ביטול תור** — ביטול תור ע"י הווטרינר מייצר אוטומטית הודעה בצ'אט של הבעלים, בחיבור בין מודול התורים למודול ההודעות.
4. **פורטלים נפרדים לפי תפקיד** — התצוגה, התפריט ומסלולי הניווט משתנים לחלוטין לפי תפקיד המשתמש, בשני הלקוחות.
5. **מרכז התראות בתוך המערכת** — בנוסף להתראות ה-Push, קיימות התראות פנימיות עם סימון כנקרא ומחיקה, בפעמון התראות באתר ובמסך ייעודי באפליקציה.
6. **דו-לשוניות מלאה (עברית/אנגלית) ותמיכת RTL** בשני הלקוחות — דרישה שלא הופיעה באפיון המקורי.
7. **מטמון מקומי באפליקציה** המאפשר הצגת חיות ותורים גם כאשר הרשת אינה זמינה.
8. **לשונית מרשמים ומסמכים** בפרופיל החיה, בנפרד מההיסטוריה הרפואית הקלינית.
9. **שדות מעקב נוספים בפרופיל החיה** — משקל ותאריך החיסון הבא.
10. **קו עיצובי אחיד** בין האתר לאפליקציה, שעבר מספר איטרציות מתועדות.

## 6. הבדיקות שבוצעו

לאורך כל הפיתוח בוצע תהליך בדיקות ידני מקיף, שליווה כל יכולת מרגע מימושה. הבדיקות בוצעו לאחר כל פיתוח של יכולת חדשה וכן לאחר כל תיקון משמעותי, במטרה לוודא את תקינות המערכת לפני המעבר לשלב הבא. הבדיקות כללו:

- **בדיקות פונקציונליות של כלל המסכים** בשני הלקוחות — אתר ואפליקציה.
- **בדיקות הרשמה והתחברות**, כולל ולידציות שדות, טיפול בקלט שגוי והודעות שגיאה למשתמש.
- **בדיקות הרשאות (Owner / Vet)** — אימות שהפרדת התפקידים נאכפת בפועל: כתיבת רשומות רפואיות והעלאת מסמכים שמורות לווטרינר, הבעלים רואה אך ורק את חיותיו ותוריו, ומסלולים ייעודיים חסומים לתפקיד שאינו מורשה.
- **בדיקות ניהול חיות מחמד** — הוספה, עריכה, מחיקה וצפייה בפרופיל.
- **בדיקות רשומות רפואיות** — הזנה, עריכה, סינון לפי סוג רשומה וצפייה מצד הבעלים.
- **בדיקות קביעת, שינוי וביטול תורים**, כולל הצגת חריצים פנויים בלבד וחסימת מועדים שחלפו.
- **בדיקות שיחות וידאו** מקצה לקצה בין הבעלים לווטרינר.
- **בדיקות מערכת ההודעות** — שליחה, קבלה, סימון כנקרא ורשימת השיחות.
- **בדיקות התראות** — התראות בתוך המערכת והתראות Push למכשיר.
- **בדיקות העלאת תמונות ומסמכים** — תמונות פרופיל וקבצי PDF, לרבות התנהגות המערכת מול סוגי קבצים שאינם מורשים.
- **בדיקות חיפוש וטרינרים** — חיפוש מטופל לפי ת"ז ואיתור וטרינרים זמינים לפי מיקום.
- **בדיקות אינטגרציה מול השרת** — אימות ישיר של נקודות הקצה ושל מבנה התשובות, בהתאם לשלבי בדיקה מתועדים.
- **בדיקות על מכשירי Android** — הרצה ובדיקה על מכשיר ואמולטור. בעץ העבודה נותרו תוצרי בדיקה (צילומי מסך ודוחות היררכיית מסך) המשמשים ראיה לבדיקות שבוצעו על המכשיר.
- **בדיקות תרחישי שימוש מרכזיים** — מעבר על הזרימות המלאות שהוגדרו במסמך הדרישות, משני צדי המערכת.
- **בדיקות תרחישי קצה** — התנהגות ללא חיבור רשת, זמני תגובה ארוכים, קלט חריג בשדות מספריים, ומעבר בין עברית לאנגלית לאימות פריסת RTL.
- **בדיקות חוזרות (Regression Testing)** — לאחר כל תיקון משמעותי בוצע סבב בדיקות נוסף על הזרימות המרכזיות, כדי לוודא שהתיקון לא פגע בפונקציונליות קיימת. תהליך זה משתקף בהיסטוריית הגרסאות של הפרויקט.

בסיום סבבי הבדיקות הידניות נמצאה המערכת יציבה, ולא נותרו תקלות קריטיות ידועות במועד ההגשה. לצד זאת, היקף הבדיקות **האוטומטיות** בפרויקט מצומצם יחסית ומתמקד בלוגיקה טהורה — ולידציית תעודת זהות בצד השרת. הרחבת הכיסוי האוטומטי, ובכללה בדיקות אינטגרציה ובדיקות ממשק אוטומטיות, היא כיוון ההמשך הטבעי של הפרויקט.

## 7. הוראות הרצה קצרות

**Backend**
```bash
cd backend
npm install
npm start
```
נדרש קובץ `.env` עם פרטי החיבור למסד הנתונים ולשירותי הענן.
לזריעת נתוני דמו: `npm run seed` — יוצר משתמש וטרינר (`vet@clinic.com / vet123`) ומשתמש בעלים (`owner@test.com / owner123`) לצורך בדיקת המערכת.

**Website**
```bash
cd web-app
npm install
npm run dev
```

## 8. סיכום

VET4PET מממשת פלטפורמה בארכיטקטורת Client-Server הכוללת שני לקוחות — אפליקציית אנדרואיד נייטיב ואתר אינטרנט — הפונים לשרת REST משותף מעל מסד נתונים מסמכי. כל היכולות הפונקציונליות שהוגדרו במסמך הדרישות מומשו, לרבות אלה שסומנו במקור כאופציונליות (ייעוץ וידאו) ואלה שסומנו במסמך ה-PROTOTYPE כפערים פתוחים (התראות Push ואיתור מרפאות חירום לפי מיקום). מעבר לכך נוספו יכולות שלא נכללו בתכנון המקורי, ובראשן ניהול זמינות גרנולרי ליומן הווטרינר, מודל חיפוש מבוסס תעודת זהות שנועד לשמור על חיסיון רפואי, ותמיכה דו-לשונית מלאה בשני הלקוחות.

המערכת נבדקה לאורך כל הפיתוח בתהליך בדיקות ידני מקיף, בשילוב בדיקות חוזרות לאחר כל תיקון משמעותי. הרחבת הכיסוי האוטומטי וחיזוק מנגנון מניעת ההתנגשויות בהזמנת תורים הם כיווני ההמשך העיקריים לפיתוח עתידי של המערכת.

הפרויקט הושלם בהתאם למטרות שהוגדרו, תוך מימוש כלל היכולות המרכזיות והרחבתו במספר יכולות נוספות מעבר לאפיון המקורי. אנו מאמינים כי התוצאה הסופית מספקת מערכת יציבה ושימושית, המהווה בסיס טוב להמשך פיתוח בעתיד.
